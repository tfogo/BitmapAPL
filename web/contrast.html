COMPARISONS, COUNTS, AND RUNNING TOTALS

Counting the light

A whole picture can help us choose what to do with one pixel.

So far, we have asked each pixel’s neighbors for help. This time we’ll count brightness values across the whole image. APL’s comparisons and running totals give us a way to turn those counts into contrast.

Start with eight pixels. Their values range from 2 to 6. Move the slider to count them, one at a time.

A comparison makes a mask

We’ve seen lists of zeros and ones select values. A comparison can make one of those lists. Here, = asks which values equal 3:

values ← 2 2 3 3 3 5 6 6
values=3
⍝ 0 0 1 1 1 0 0 0

Add the ones and we have a count. There are three pixels with value 3.

+/values=3              ⍝ 3

Read it from the right: compare first, then sum. No new kind of loop is needed.

Ask the same question of each level

We can put the question in a function and apply it to each brightness level. The two dots ¨, called Each, do that for us.

⎕IO ← 0
Count ← {+/values=⍵}
counts ← Count¨⍳8
⍝ 0 0 2 3 0 1 2 0

⍳8 supplies levels 0 through 7. Each calls Count once for every level. The resulting list is a histogram: how often each value appears.

Our library uses 256 levels for an 8-bit grayscale image. The small diagram uses eight so we can see every count.

A slash keeps the sum. A backslash keeps the steps.

+/ gives the final sum. Replace the slash with a backslash and +\ keeps the running totals. This operator is called scan.

+/counts                ⍝ 8
+\counts                ⍝ 0 0 2 5 5 6 8 8

At level 3, the running total is 5. Five of our eight pixels have brightness 3 or less. Sweep across the histogram to see these totals build.

This is a cumulative histogram. Unlike a neighborhood filter, it describes the whole image. Moving the pixels around would not change it.

Turn the totals into a table

Our pixels occupy a small part of the available brightness range. We can use the running totals to spread their values out.

The first occupied level is 2, with a running total of 2. Subtract that total so the darkest pixels map to zero. Divide by the remaining count, 6, then scale to 255.

running ← +\counts
first ← 2               ⍝ first nonzero running total
scaled ← 255×(0⌈running-first)÷8-first
mapping ← ⌊0.5+scaled
⍝ 0 0 0 128 128 170 255 255

0⌈ keeps the value from going below zero. Adding 0.5 and taking the floor with ⌊ rounds to an integer. The histogram decides the spacing: a more common level makes a larger jump in the running total.

Now square brackets do the rest. The values in our image become positions in the table:

mapping[values]
⍝ 0 0 128 128 128 170 255 255

Every pixel with the same input value gets the same output value. The order stays intact: a darker input never becomes brighter than a lighter one.

Give the picture more room

This is histogram equalization. Here it is on a larger image whose brightness values sit close together. Drag the dividing line to compare the same locations.

Below are the counts before and after the change. Each bar groups four adjacent brightness levels so the plot fits on the page.

result ← ImageOps.Equalize picture
result.histogram
result.cumulative
result.mapping
result.output

The function returns the intermediate arrays as well as the picture, so we can inspect each step. It accepts integer grayscale values from 0 to 255.

If every pixel has the same value, there is no range to spread out. The divisor would be zero. The library handles that case by leaving the image unchanged.

Despite its name, equalization does not guarantee equal-sized histogram bars. All pixels with one input value move together. It can reveal detail, but it can also exaggerate noise or make a picture look harsh. It cannot recover detail that was never recorded.

This example works on grayscale. Applying different mappings to red, green, and blue can change a picture’s colors. Color equalization needs a separate choice about which quantity to change.

We used = to ask a question, ¨ to ask it of each level, +\ to keep running totals, and indexing to apply the answer. A few array operations carried us from counting pixels to changing a whole picture.

About this walkthrough

The browser model is checked against 28 executed Dyalog cases, including counts, running totals, mappings, and output pixels. It does not execute APL in the browser. The count animation illustrates accumulation; it does not show the interpreter’s execution order. All motion is controlled by the sliders.

The landscape is generated from fixed shapes and brightness gradients. The mapping subtracts the first occupied cumulative count, scales to 0–255, and rounds halves up. Constant images remain unchanged.
